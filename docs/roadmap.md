# 新功能实现评估（Roadmap / 可行性分析）

> 来源：`docs/1.md`《项目功能规格说明书：动态站点构建系统》
> 状态：**仅评估，未实现、未动代码**
> 日期：2026-09

## 总体判断

目标是从「SSR 博客」演进为「可扩展 CMS 平台」。体量巨大，完整实现相当于一次**架构级改造**，而非小迭代。

当前架构的结构性约束：

1. **web 是 Astro SSR**（`output: 'server'`），页面为构建时/运行时模板，页面是**静态 `.astro` 文件** + `[slug].astro` 动态路由，**不是内容驱动的动态布局引擎**。要实现「全 UI 骨架热切换 / SPA 局部刷新 / 拖拽布局」，需要一个**运行时布局渲染层**（当前不存在）。
2. **Cloudflare Workers 运行时硬限制**：脚本体积（3MB 压缩）、CPU 时间、无法任意外装 npm 模块或原生解压 zip。规格书里的「上传 zip 主题、运行时注入任意插件代码」会踩**安全 / 体积 / 性能 / 隔离**多重红线。
3. **admin 是 SPA、web 是独立 SSR**，渲染体系不同；「后台切换主题并热更新前台」需打通**运行时配置 → 前台渲染**通道（当前仅有 `config` 读 KV 缓存）。

## 架构现状（依据）

- monorepo：`web`（Astro SSR，前端）/ `server`（Hono Worker，公开 API + 后台 API + 托管 admin SPA）/ `admin`（React SPA，`/admin/`）。
- server 仅 Hono API 层：`/admin/api/*`、`/api/public/*`；后台页面由 `ASSETS` binding 托管。
- 数据：Cloudflare D1（SQLite）/ R2 / KV。
- DB 分层：`db/schema/` 下有 `content / user / taxonomy / engagement / config` 等。
- web 页面：静态文件（index/about/links/message/hitokoto…）+ 动态（posts/categories/tags + `[slug]`）。

## 模块 1：主题模板引擎（动态主题系统）

| 子项 | 工作量 | 说明 |
|------|:---:|------|
| 多主题 CSS 变量热切换 | 已完成 | 现有 `data-skin` 体系（default/ocean/forest/sunset/midnight） |
| 全 UI 骨架更换（非仅 CSS） | **高** | 需把 Astro 布局抽成「多套运行时可选 Layout」（Header/Sidebar/Footer/列表样式各不相同） |
| 上传 .zip 主题包 + 解压 + 校验 | **高** | Worker 无内置解压；需引 JS 解压库，且任意 HTML/JS 注入**安全风险极高** |
| URL / Git 在线安装 | 中 | 出站请求 + 仓库解析 + 来源/信任校验 |
| 主题配置变量动态表单 | 中 | `theme.json` 声明变量 → admin 动态表单 → 存 JSON |
| 局部热重载（仅内容区，SPA 体验） | **中—高** | 与 Astro SSR 冲突，需客户端路由/渐进增强 |

- **可行性**：多套**内置**主题（骨架级）**可行**；任意第三方 zip + 任意模板在 Worker 上**受限且高风险**，建议砍掉或降级为「仅内置主题」。
- **预估**：内置多主题全骨架切换 + 配置变量表单约 **3–5 天**；加 zip/URL 第三方主题**另加 5–10 天**（安全收益差）。

## 模块 2：组件 / 插件管理器（模块化架构）

| 子项 | 工作量 | 说明 |
|------|:---:|------|
| 启用/停用 + 前台/后台路由屏蔽 | 中 | `plugins`/`components` 表 + 状态位 + 渲染判断 |
| 依赖检测（Node / 核心版本） | 中 | 元数据 + 校验 |
| 卸载数据清理开关 | 中 | 事务 + 按需 drop |
| 业务插件（SEO/Sitemap/统计） | 中 | 现有 config 已有部分能力，可映射成「内置插件」 |

- **可行性**：内置插件/组件（白名单、预编译）**可行**；「任意第三方插件运行时插代码」在 Worker 上**基本不可行**（无动态安装、无法跑任意模块、安全隔离难）。
- **预估**：内置模块管理框架 + 2–3 个示例插件约 **4–6 天**。

## 模块 3：可视化页面构建器（拖拽生成）

| 子项 | 工作量 | 说明 |
|------|:---:|------|
| 自定义页面 CRUD + 层级路由（/products/phone） | 中 | 需把 web 改为「DB 兜底解析」（当前静态路由文件，需加 catch-all） |
| 拖拽画布 + 实时预览 + 属性面板 | **高** | 最重部分，接近 mini 低代码引擎 |
| 区块库（布局/内容/动态数据） | 高 | 每类需渲染器 + 配置器 |
| 样式隔离 / 数据源绑定 / 自定义 HTML | 高 | scoped 样式注入 + 动态数据查询 + 用户 HTML（XSS 风险） |
| 草稿/发布 + 定时发布 | 中 | 复用 posts 的 status 模型 + schedule 字段 |
| 版本历史 | 规格注明「待定」 | — |

- **可行性**：「JSON 结构化的页面定义 + 服务端渲染器」可实现一个**受限**的区块构建器（更接近「区块序列」而非自由拖拽）。真正自由的拖拽 / WYSIWYG 在 Worker + SSR 下**工作量大且体验打折**。
- **预估**：MVP（JSON 区块页面 + 层级路由 + 草稿/发布 + 基础区块库）约 **8–12 天**；完整拖拽画布 + 深度样式隔离 + 数据源绑定 **15–20 天以上**。

## 汇总

| 模块 | 完整实现 | MVP/降级版 | 主要风险/障碍 |
|------|:---:|:---:|------|
| 1 主题引擎 | 12–20 天 | 4–6 天（内置骨架级主题） | Worker 上第三方 zip 主题安全/性能 |
| 2 组件/插件管理 | 6–9 天 | 4–6 天（内置插件） | 动态安装任意插件不可行 |
| 3 页面构建器 | 20–30 天 | 8–12 天（JSON 区块页面） | 拖拽 WYSIWYG + SSR 渲染体系冲突 |
| **合计** | **约 6–9 周** | **约 3–5 周** | 见下 |

> 估算按「单人全力、熟悉现有代码」计；不含联调 / 部署 / 回归测试。

## 三点建议

1. **砍掉或降级「第三方 zip / 任意插件 / 自由拖拽」**：这三块与 Cloudflare Worker 运行环境限制根本冲突，强做会踩安全（任意 HTML/JS 注入）与体积/性能红线。建议改为 **内置主题 + 内置白名单插件 + JSON 数据库驱动的「区块页」**，可控且安全。
2. **先做「内容路由层」**：给 web 加 catch-all 路由，把 `/slug`、层级路径从「静态文件」改成「查 DB」——这是模块 1 与 3 共同的地基，先做收益最大。
3. **分阶段交付**：建议按「主题骨架切换 → 内容路由层 → 插件框架 → 区块页面构建器」排产，每阶段独立可上线。
